# B3-1 동료평가 4-4 — AWS 비용 원인 추적과 실제 자원 정리

> **실습 리전:** 서울(`ap-northeast-2`)  
> **비용 확인:** 2026-11-19  
> **기존 실습 자원 삭제:** 2026-11-20  
> **주의:** 2026-11-20에 **기존 환경을 삭제한 뒤 평가용 새 환경을 다시 구축**했다. 아래의 "삭제 완료"는 **기존 자원 ID에만 적용**하며, 새 자원까지 삭제했다는 뜻이 아니다.

## 1. 평가 질문

**AWS Billing 화면에서 예상하지 못한 비용이 발생했다면, 어떤 클라우드 자원부터 의심하고 어떻게 원인을 추적하고 정리할지 설명할 수 있는가?**

쉽게 말해 **요금 확인 → 원인 찾기 → 안전하게 정리 → 결과 검증**을 설명하는 문제다.

## 2. 실제 Billing 확인 사례 (2026-11-19)

AWS Billing에서 2026년 11월의 **크레딧 적용 전 사용료 약 USD 1.34**를 확인했다. 처음에는 다른 리전 사용이나 집/아카데미 IP를 모두 SSH 허용 목록에 넣어서 비용이 생긴 것으로 추측했지만, 서비스별 상세 항목을 확인해 원인을 구분했다.

| 과금 자원 | 확인한 사용량·단가 | 크레딧 적용 전 사용료 |
| --- | --- | ---: |
| EC2 Linux t3.micro | 70시간 × $0.013/시간 | $0.91 |
| EBS gp3 | 0.778 GB-month × $0.0912/GB-month | $0.07 |
| 공인 IPv4 주소 | $0.005/시간, 두 사용량 구간 | $0.36 |
| **합계** | | **$1.34** |

- **검증:** Billing → 청구서 → 서비스별 요금에서 EC2 **$0.91**, EBS **$0.07**, 공인 IPv4 **$0.36** 확인.
- **크레딧:** 당시 화면에서 Free Tier 크레딧 **−$1.34**가 적용되어 위 세 항목의 사용료를 상쇄했다.
- **오해 바로잡기:** SSH 보안 그룹에 공인 IP 주소 **두 개를 '허용'**해도 EC2에 공인 IPv4 주소 두 개가 할당되는 것은 아니다.
- **EIP 확인:** 서울 리전의 Elastic IP 목록이 비어 있었다. **EIP를 만든 적이 없으므로 삭제한 것으로 세지 않는다.** EC2에 자동 할당된 일반 공인 IPv4 주소에서도 사용료가 계산될 수 있다.
- **비용 주의:** **$1.34는 사용료 계산액이지 최종 결제액 확정치가 아니다.** 무료 크레딧 적용과 월말 청구액은 구분해야 한다.

## 3. 증상 → 가설 → 검증 → 조치 → 결과

1. **증상:** 예상하지 못한 AWS 사용료 약 **$1.34**가 보여 비용 발생 원인이 궁금했다.
2. **가설:** EC2 실행 시간, EBS 저장 공간, 공인 IPv4 주소가 원인일 수 있다고 생각했다.
3. **검증:** Billing 서비스별 요금을 펼쳐 각 항목의 사용료를 확인하고, Free Tier 차감 내역도 확인했다. Elastic IP는 별도로 생성되지 않았음을 목록에서 확인했다.
4. **조치:** 필요한 서비스 동작·삭제 전 증빙을 보관하고, **2026-11-20 기존 실습용 EC2를 종료**한 다음 EBS 삭제 여부를 확인했다. 이어 **기존 실습 VPC와 연결된 네트워크 자원**을 삭제했다.
5. **결과:** **기존 환경에서 총 7종류 자원 정리**를 확인했다. 단, 삭제 직후 청구액이 즉시 0원이 되는 것은 아니며, **최종 청구액은 별도 재확인 필요**하다.
6. **재발 방지:** 실습 종료 후 불필요한 자원은 **자원 ID로 식별해 정리**하고, AWS Billing·예산 알림을 정기적으로 확인한다.

| 인터넷 게이트웨이 | `igw-03cd847dd8c2ea224` | VPC 삭제 시 함께 정리 |
| 라우트 테이블 | `rtb-04b0e56289f04d61b` | VPC 삭제 시 함께 정리 |
| 보안 그룹 | `sg-0c2b0be06285043eb` | VPC 삭제 시 함께 정리 |

**정리 순서와 이유**

1. **증빙 보관:** 삭제하면 이전 화면이나 데이터에 다시 접근하기 어렵기 때문이다.
2. **EC2 종료:** 실행 중인 서버를 먼저 정리하고 연결 자원의 의존 관계를 줄이기 위해서다.
3. **EBS 삭제 확인:** EC2를 종료해도 별도 볼륨이 남아 비용이 발생할 수 있으므로 목록으로 확인한다.
4. **VPC와 네트워크 자원 정리:** 실습용 VPC 삭제 화면에서 함께 삭제되는 서브넷·IGW·라우트 테이블·보안 그룹의 ID를 확인하고 정리했다.
5. **결과 및 청구액 확인:** AWS의 삭제 성공 메시지와 해당 자원 목록을 확인했다. **요금 청구 반영에는 시간이 걸릴 수 있으므로 Billing도 다시 점검해야 한다.**

**실제로 남길 것과 구분할 것:** 기본 VPC나 다른 프로젝트의 자원은 삭제하지 않았으며, Elastic IP는 **미생성**이었다. IAM 사용자 및 키 페어 등은 별도 판단 대상으로 남겨 두었다.

## 5. 새로 만든 평가용 환경과 혼동하지 않기

기존 환경을 정리한 **같은 날인 2026-11-20**, 실시간 동작 시연을 위해 새 자원을 다시 만들었다.

| 구분 | 새 평가용 자원 (기존 삭제 목록과 별개) |
| --- | --- |
| EC2 | `i-0c21b5e53981b3509` |
| VPC | `vpc-0d88bc20ed9a62acf` |
| 퍼블릭 서브넷 | `subnet-08cefe9ef7e68efb1` |
| 인터넷 게이트웨이 | `igw-0e4d6912fe6419060` |
| 라우트 테이블 | `rtb-0d80243f59d37e5f7` |
| 보안 그룹 | `sg-05be7398086120937` |
| 당시 EC2 공인 IP | `54.180.144.198` |

**2026-11-20 당시 새 EC2의 실행·SSH·Nginx 외부 접속을 확인했다.** 이 자료만으로 **2026-11-21 현재도 실행 중인지 또는 이미 정리됐는지까지 확정할 수는 없다.** AWS 콘솔의 현재 상태를 확인한 뒤 실습 종료 시 새 환경 역시 정리해야 한다. 이 기간의 사용료도 별도로 발생할 수 있다.
